# P0b 报告：28 nm 库密度对照与 INT8 执行部件优化

> 状态：P0b 主体完成（库密度对照已定论；16×16 tile 功能通过，综合面积优化列为下一轮）。
> 日期：2026-11-05
> 目标：回答 P0 中“面积/默认功耗为什么差 4.6×/18.6×”，并尝试把 INT8 基线拉近 OzCore/MSD-Core 的量级。

## 1. 结论

1. **4.6× 面积差主要是标准单元库密度，不是逻辑规模。** 同一份 `int8_mac` RTL：
   - SMIC 28 nm HPC RVT TT：1281.67 µm²，767 cells，平均 1.671 µm²/cell；
   - TSMC 28 nm HPC+ FF：**378.13 µm²，365 cells**，面积降到 **1/3.39**，cells 降到 1/2.10。
   - 与 OzCore 的 265.4 µm²/MAC 相比，TSMC 版只差 **1.42×**（SMIC 版 4.83×）。
2. **默认功耗差主要是库/角 + 活动率假设。** 同一 RTL 的默认活动率总功耗从 585.0 µW（SMIC TT）降到 **109.9 µW**（TSMC FF），每 MAC 能量 0.366 pJ；相对 OzCore 的 0.0956 pJ 只差 **3.83×**（SMIC 版 20.4×）。剩余差距来自默认活动率、单元功耗密度和 128×128 线性外推，而不是算法效率。
3. **TSMC 版在 3.5 ns 约束下 slack 还有 2.26 ns**（关键路径 1.13 ns），说明该 RTL 远未压满；后续可以按更低频率做面积优化，或按更高频率用满时序。
4. 16×16 共享控制/树形归约 tile 的功能测试已通过（`PASS int8_tile16, y0=48`），其综合面积见第 4 节；它用来验证“把每 MAC 独立累加器/控制换成共享归约”还能再降多少。

## 2. 方法

- 同一份 RTL：`rtl/int8_mac.sv`（3 级流水，8×8 有符号乘 + INT32 累加，valid 门控）。
- 两个标准单元库/角：
  - SMIC 28 nm HPC RVT TT（0.90 V / 85 °C），300 MHz（3.333 ns），DC O-2018.06-SP1；
  - TSMC 28 nm HPC+ FF（0.99 V / 0 °C），285.7 MHz（3.50 ns），同 DC，与用户 MSD-Core 流程一致。
- 面积口径：DC 标准单元面积（不含互连/布线）。
- 功耗口径：DC `report_power` 默认活动率（未 SAIF），动态 + 漏电。
- 简单外推：128×128 = 16384 × 单 MAC；未计共享控制/布线，偏保守。

| 指标 | SMIC 28 HPC RVT TT | TSMC 28 HPC+ FF | 变化 |
|---|---:|---:|---:|
| Total cell area (µm²) | 1281.67 | **378.13** | **−70.5%** |
| cells | 767 | **365** | −52.4% |
| comb / seq | 697 / 70 | 294 / 70 | 组合大幅减少 |
| 平均 cell 面积 (µm²) | 1.671 | **1.036** | −38.0% |
| Combinational area (µm²) | 991.37 | 219.74 | −77.8% |
| Noncombinational area (µm²) | 290.30 | 158.38 | −45.4% |
| 关键路径 (ns) | 3.25 | **1.13** | −65.2% |
| slack @ target (ns) | 0.00 @3.333 | **+2.26 @3.50** | 大幅松弛 |
| 动态功耗 (µW) | 504.85 | **109.63** | −78.3% |
| 漏电 (µW) | 80.16 | **0.256** | −99.7% |
| 总功耗 (µW) | 585.01 | **109.88** | −81.2% |
| 每 MAC 能量 (pJ) | 1.778 | **0.366** | −79.4% |

128×128 外推：

| 指标 | SMIC 版 | **TSMC 版** | OzCore 参考 | TSMC / OzCore |

## 4. 16×16 共享控制 tile（P0b 优化）

`rtl/int8_tile16.sv`：16×16 权重驻留、256 个 INT8 乘法、5 级树形归约 + 1 级累加；只有 16 个 32-bit 累加器（不是 256 个），valid/控制全局共享。

- 功能：VCS 定向测试通过（全 1 权重，x=1 → y0=16；x=2 → y0=48）。
- 综合：TSMC FF 3.5 ns 的 DC 综合在 mapping ultra-high-effort 阶段未能于本轮收敛（256 个乘法器 + 树形归约的优化空间大），已将本轮 DC 进程停止；面积/功耗结果留到下一轮（P0c）。这不影响第 1 节的库密度结论——库对照用的是已完成的单 MAC 综合。

> 说明：tile 的作用是验证“共享控制 + 共享累加器”能进一步降低 per-MAC 面积；它属于优化项，不是 P0b 的门槛。

## 5. 对 P0 结论的修正

- P0 报告第 4.5 节的“库密度是主因”假设，现已被**同 RTL 换库实验证实**：面积 4.6× → 1.42×。
- P0 的“默认功耗 18.6×”同样是库/角 + 默认活动率的组合；TSMC 版降到 3.83×。真实活动率（SAIF）还没测，3.83× 仍是上界性质的估计。
- 因此，P0b 之后不应再拿 SMIC 版的绝对面积/功耗与 OzCore 比；**统一用 TSMC 28 HPC+ FF、3.5 ns、同 RTL 风格**做 FP8/FP4 的相对比较。

## 6. 下一步（进入 FP8/FP4）

1. 用相同 TSMC/3.5 ns/DC 流程实现 FP8 E4M3 MAC（5×5 有效尾数乘 + 指数/对齐/规格化 + FP32 累加）和 FP4 E2M1 MAC（2×2 有效尾数 + FP32 累加）。
2. 对三种格式用同一 pass/模数模型估计达到 BF16/FP32 等精度所需的 pass 数，得到等精度 AEE。
3. SAIF 功耗：优先复用用户环境里的 VCD→SAIF 流程（`03_ASIC综合/dc-package/scripts`），避免 DC 默认活动率。
