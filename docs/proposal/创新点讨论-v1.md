# 创新点逐条讨论（v1）

> 目的：在开题报告 v1.1 的基础上，对四条创新点做“审稿人视角”的压力测试，而不是重复主张。
> 每条给出：一句话主张、OzCore 已有什么、本文增量、最强质疑、需要什么证据、需要你拍板的问题、我的初步判断。

## I1 精度虚拟化与硬件合同

**一句话主张**：把目标格式、误差界、动态范围变成硬件可执行、可验证的合同；硬件自动选 N/基/缩放，并用守卫与统计保证合同。

**OzCore 已有什么**：s 是运行时寄存器，支持 {2,3,4,6,12} 的重构吞吐切换；前/后处理已整数化。

**本文增量**：
- 应用级语义：EXACT / BOUNDED(ε) / FAST；
- 最坏情况守卫：缩放上界 vs P/2、重构后范围检查、越界增大 N 或回退；
- 精度统计回读：ulp 分布、正确舍入比例、实际 N/基/缩放；
- 合同跨 INT8/FP8/FP4 基生效。

**最强质疑**：cuBLAS ADP 已经在软件层做“自动选 N + 回退 + 默认精度不低于原生”；把同样逻辑放进硬件状态机，是否只是工程迁移？审稿人会问：**没有硬件合同，软件 ADP 做不到的具体是什么？**

**需要什么证据**：
- 对抗输入/极端动态范围下，软件 ADP 的估计失效而硬件守卫能提前拦截的案例；
- 同一 DGEMM 在 EXACT 与 BOUNDED(2 ulp) 下吞吐差 ≥1.5×，且统计与 MPFR 一致；
- 合同违反时的回退开销可测、可证明。

**需要你拍板**：目标用户是科学计算（要求正确舍入/最坏界）还是 LLM（允许容差）？这决定合同语义的重心。若两者都要，是否接受“EXACT 模式吞吐较低、BOUNDED 模式用于推理”的双档设计？

**我的判断**：**中强**。核心增量不是“运行时选 N”（OzCore 已有 s），而是“最坏情况保证 + 跨基 + 可回读统计”。若只讲“自动选参”，会被 ADP 覆盖；若讲“硬件守卫在最坏输入下保证合同”，才有独立价值。

## I2 多基可重构阵列与硬件感知选基

**一句话主张**：同一阵列支持 INT8/FP8/FP4 运行时选择，用相图回答“平台/负载 → 最优基”。

**OzCore 已有什么**：INT8-only 阵列；证明统一整数阵列的可行性。

**本文增量**：
- 同一 RTL 支持三基，后端共享 CRT/加权；
- 选基相图与运行时启发式；
- 覆盖 B300/Rubin 类“INT8 峰值被削减、FP8/FP4 主导”的平台。

**最强质疑**：B300/Rubin 的峰值比是 **GPU 厂商的产品选择**；如果我们在做 **自研 ASIC**，INT8/FP8/FP4 的峰值比是我们自己设计的，为什么要把“平台峰值比”作为选基依据？更尖锐地说：我们自己的实测（28 nm）显示 INT8 在等精度下最优；多基只会增加面积（FP8/FP4 MAC 为 INT8 的 1.46–1.64×，阵列 1.63–1.82×），**在自研 ASIC 上可能是不必要的开销**。

**需要什么证据**：
- 目标平台的峰值比是“给定约束”还是“设计变量”？如果是设计变量，I2 的论证必须改为“工作负载组合”而不是“平台峰值”；
- 混合负载（FP64/FP32 科学计算 + FP8/FP4 推理）下，同一阵列的利用率提升能否抵消多基面积；
- 三基切换的面积/能耗开销上限（例如 ≤15%），以及“不做多基、只做 INT8 + 软件分解”的对照。

**需要你拍板**：目标硬件是 **自研 ASIC** 还是 **面向现有 GPU/加速器平台**？
- 若自研 ASIC：I2 应改为“统一阵列同时服务高精度模拟与原生低精度模式”，用工作负载组合论证；否则建议把多基降为 WP6 增量，主线保 INT8。
- 若面向 GPU 类平台：I2 的“平台峰值比”论证成立，但需要明确我们做的是加速器 IP/子系统，而不是独立 ASIC。

**我的判断**：**按当前写法偏弱**。它像一个“把 FP8/FP4 也加上”的工程扩展，且与我们的实测（INT8 等精度最优）有张力。要么用“混合负载/原生低精度模式”重新论证，要么降级为增量工作包。

## I3 端到端单遍融合与存储层次协同

**一句话主张**：FTU + 阵列 + CRT epilogue 单遍融合，余数平面片上双缓冲，避免 N 倍 HBM 中间矩阵。

**OzCore 已有什么**：三阶段流水线（preprocess → INT8 GEMM → postprocess），前/后处理全流水，且明确说 pipeline fill latency 相对 GEMM tile 可忽略。也就是说，**OzCore 很可能已经做到了 tile 级融合**。

**本文增量**（需要重新聚焦）：
- 指数感知取模：用尾数模 + 2 的幂模表，避免物化 110-bit 整数；
- 尺度不变 fast-mode 缩放的硬件实现；
- 多基 limb 编码（base-13）与统一后端；
- 面向 1024–4096 的“困难区间”做 SRAM/带宽协同，而非只报大规模 GEMM。

**最强质疑**：如果 OzCore 已经是 tile 级流水、前/后处理都在片上，“避免 N 倍 HBM 中间矩阵”就不是本文的独有增量；审稿人会问：**你和 OzCore 的数据流到底差在哪？** 需要逐条对照 OzCore 的 pre/post 数据流，而不是假设它把中间平面写回 HBM。

**需要什么证据**：
- 复现/推导 OzCore 的 tile 数据流，明确它是否物化 N 个平面；
- 在 1024–4096 上，OGE 的非 GEMM 开销与 OzCore 报告值的对比；
- FTU 的指数感知取模/尺度不变缩放的面积/吞吐优势（相对通用宽整数实现）。

**需要你拍板**：是否接受把 I3 从“无 HBM 中间矩阵”改为“**FTU 的指数感知/尺度不变 + 小中矩阵存储协同**”？前者容易被 OzCore 的 tile 流水覆盖，后者更具体、可验证。

**我的判断**：**中等**。当前表述有被 OzCore 覆盖的风险；“无 HBM”需要证据。真正的硬增量在 FTU 的取模/缩放与多基 limb，而不是“融合”这个宽泛词。

## I4 同面积可行性包络与 RTL 级证据

**一句话主张**：用目标工艺综合 a₆₄/a₃₂，建立同面积/同功耗/同带宽/同精度保证的对比框架，回答“统一引擎是否真的占优”。

**OzCore 已有什么**：相对融合多格式基线的等精度比较；没有相对同面积原生 FP64/FP32 的对照。

**本文增量**：
- a₆₄/a₃₂/e₆₄/e₃₂ 的目标工艺标定；
- 同面积归一化框架与可行性包络；
- RTL/综合/模拟证据，而非 projected floor。

**最强质疑**：这是一个 **评估方法学** 贡献，但体系结构顶会通常要求“方法学 + 新设计 + 强结果”三合一；如果 a₆₄ 只有 20 左右、N=14–16，包络可能显示“统一引擎只打平/仅能效占优”，论文的“加速”卖点不成立。审稿人会问：**如果结论是负面的，这篇论文还成立吗？**

**需要什么证据**：
- M1 的 a₆₄/a₃₂ 综合数据（这是硬门槛）；
- 在 a₆₄ 的典型区间（20–60）给出加速比/能效比的完整曲线，而不是单点；
- 至少一个“即使纯计算不占优，系统利用率/能效/灵活性仍占优”的量化场景。

**需要你拍板**：如果 M1 显示 a₆₄ < 阈值，是否接受 **FP32-first** 或 **“负结果/测量论文”** 作为博士主线？这决定 I4 是“主创新”还是“评估章节”。

**我的判断**：**强，但高风险**。它补的是领域真实缺口（同面积公平比较），但结果可能不支持“统一引擎更快”。需要提前接受“能效/灵活性/负结果”也是可发表结论，否则会在 M1 被动。

---

## 讨论顺序建议

1. **先定 I2 的目标平台**（自研 ASIC vs 现有平台）——这决定多基是核心还是增量。
2. **再定 I1 的用户**（科学计算正确性 vs LLM 容差）——这决定合同语义。
3. **然后核对 I3 与 OzCore 的数据流差异**——这决定“无 HBM”能否作为主张。
4. **最后用 M1 的 a₆₄/a₃₂ 决定 I4 的权重**。

## 需要你回答的四个问题

1. 目标是自研 ASIC，还是面向现有 GPU/加速器平台的 IP/子系统？
2. 主要用户是科学计算（正确舍入/最坏界）还是 LLM（容差/吞吐）？还是两者都要？
3. 是否接受把 I3 聚焦为“FTU 指数感知/尺度不变 + 小中矩阵存储协同”，而不是“无 HBM 中间矩阵”？
4. 如果 a₆₄ 低于阈值，是否接受 FP32-first 或负结果/测量论文作为博士主线？
