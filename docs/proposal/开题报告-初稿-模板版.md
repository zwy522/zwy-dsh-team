# 面向多精度统一执行的 Ozaki 模拟 GEMM 加速器关键技术研究

## 一、学位论文选题的立论依据

大模型与科学计算对矩阵乘（GEMM）的精度需求正在同时向两端扩张：一端是 FP64/FP32 的科学计算与训练梯度，另一端是 FP16/BF16/FP8/FP4/INT8 的推理与低精度训练。GPU 厂商把面积与功耗持续投向低精度，公开规格中 INT8 与 FP64 的峰值比已达到 10²–10³ 量级；而 HPC 与科学计算仍依赖 FP64，二者形成结构性矛盾。传统数据通路融合在一个 MAC 中复用多格式，每增加一种格式就增加一份大多数时间空闲的硬件，持续稀释单位面积算力。

Ozaki Scheme II 给出了另一条路线：把高精度浮点矩阵按行/列共享指数缩放为整数，对一组两两互素的模数取余，在低精度整数阵列上做精确 GEMM，再用中国剩余定理（CRT）重构。其关键性质是中间乘积精确、误差可分析、GEMM 次数随模数个数线性增长。OzCore（MICRO 2026）把该方案做成整数化的 GEMM 架构，在 INT8 阵列上仅增加 27.9% 前/后处理面积，就在 LLaMA-3.1 上匹配 BF16 困惑度，并相对融合多格式基线取得 1.91× TOPS/mm² 与 1.40× TOPS/W。

但 OzCore 留下三个工程问题。其一，小/中矩阵（K=1024–4096）的非 GEMM 开销占 27–55%：分解、取模、CRT 重构无法被 GEMM 充分摊薄，K 从 8192 降到 1024 时开销占比约升 8 倍。其二，精度由分解次数 s 隐式决定：应用只能选 s，不能声明“正确舍入/≤2 ulp/容差 ε”，也拿不到最坏情况保证与逐层误差统计。其三，N 倍余数平面带来存储/带宽压力，且缺少“同面积原生 FP64/FP32”的公平对照与 CPU+加速器的可运行系统验证。

本课题以 OzCore 为直接基线，提出 OGE（Ozaki GEMM Engine）：在 INT8-only 主阵列上，向前融合尺度不变缩放与指数感知取模，向后融合宽整数 CRT 重构与正确舍入；用“精度合同 + 硬件守卫”把精度变成可调度、可验证的资源；以小矩阵非 GEMM 开销压缩为核心，把 K=1024–4096 的困难区间压到 <10%；用同面积 a₆₄/a₃₂ 包络与 Chipyard/FireSim/U250 系统验证回答“统一引擎在什么条件下真正占优”。

预期价值：学术上，给出“精度虚拟化”的体系结构抽象、可证明的精度合同、小矩阵融合数据流与同面积评估方法，弥补现有工作“只报峰值、只对融合基线、缺少 RTL/系统证据”的不足；应用上，为 HPC 与 AI 混合负载提供一套可复用的统一 GEMM 引擎，减少独立 FP64/FP32 单元的面积闲置，提高阵列在多种精度下的利用率。

## 二、文献综述

2.1 多精度计算与精度碎片化

过去十年，矩阵引擎的峰值算力持续向低精度迁移。A100 的 INT8 峰值约为 FP64 的 64 倍，RTX 4090 达到 512 倍，B200 为 122 倍；B300 把 INT8 削减到约 150 TOPS、FP64 仅约 1.2 TFLOPS，同时把 FP4 提升到 14 PFLOPS 量级。LLM 训练/推理混合使用 BF16、FP8、FP4 与 INT8，科学计算仍依赖 FP64。精度碎片化使“一个阵列支持多精度”成为体系结构的重要问题。

数据通路融合（Bitfusion、Stripes、Laconic、UNPU 等）通过子字打包、乘法器复用、位串行/可重构数据通路支持多格式；但每增加一种格式就增加一份空闲硬件。Bitfusion 以位级可组合见长，Stripes 用位串行换取精度可调，Laconic 面向 FPGA 量化推理，UNPU 做可变权重位宽；它们都不改变 MAC 的精度语义，难以用低精度 MAC 直接获得 FP64 级精度。

2.2 Ozaki 方案：从算法到可硬件化的分解

Ozaki I 沿尾数切片，GEMM 次数随切片数平方增长；Ozaki II 用 CRT，GEMM 次数随模数线性增长。对 FP64，INT8 基下 I 约需 28–35 次 GEMM，II 约 14–16 次；FP8 基把每个模数压缩为 3 次 FP8 GEMM（12–13 个模数、36–39 次）；FP4 base-13 基利用 E2M1“加倍后为整数”的性质，用 19 个模数、75 次 FP4 GEMM 达到 FP64。

2026 年的三项进展进一步完善工程可用性：FP8 量化版、FP4 base-13 版，以及 fast-mode 缩放改进。后者指出现有 fast 公式缺乏尺度不变性，输入整体乘 2^s 会导致精度退化甚至 CRT 恢复失败，并给出零额外开销的修正。这些工作把“算法可行”推进到“可硬件化”，但软件实现仍受非 GEMM 开销与中间平面存储的制约。

从数学上看，Ozaki II 的精度由 CRT 模数乘积 P 与缩放指数共同决定：P 必须覆盖整数乘积范围，缩放必须保证截断误差与动态范围匹配；模数越多，P 越大、精度越高，但 GEMM 与 CRT 次数线性增加。fast-mode 的尺度不变性正是针对“输入整体乘 2^s 时缩放/模数不匹配”的问题；若硬件实现不处理该问题，极端动态范围下会出现 CRT 恢复失败。

Ozaki II 的 GEMM 次数由模数个数 N 决定，而 N 由目标有效位 b、内维 K 与模数位宽共同决定：对 INT8 基，N≈ceil((2b+log2 K)/8)；对 FP8 基，每个模数需 3 次 FP8 GEMM；对 FP4 base-13 基，每个模数约 4 次 FP4 GEMM。动态范围越大，缩放指数 μ/ν 的跨度越大，所需的 P 与 N 也越大；因此“同一 N 覆盖所有输入”并不成立，精度合同/动态范围自适应是必要的。

FP8 变体的关键是把模数 p≤513 的余数拆成两个 E4M3 可表示的部分，用 Karatsuba/3 次 GEMM 完成一个模数的乘积；FP4 base-13 变体则利用 E2M1 加倍后为整数、以及 13 的幂覆盖所有整数的性质，把每个元素表示为若干 base-13 limb，用 19 个模数/75 次 GEMM 达到 FP64。两者都把“低精度峰值”转化为“高精度有效吞吐”，但代价是更多的 GEMM 与更复杂的编码/重构。

多精度阵列方面，Bitfusion 用位级可组合的 MAC 支持不同位宽，Stripes 用位串行数据通路实现精度可调，Laconic 面向 FPGA 量化推理，UNPU 做可变权重位宽；这些工作证明“一套数据通路支持多精度”的可行性，但它们的精度上限仍由 MAC 位宽/累加器决定，不能直接获得 FP64 级精度。RNS/CRT 加速器多用于密码/信号处理，未与 Ozaki 的缩放/重构闭环结合。

软件/产业侧，GEMMul8 与 ozIMMU 在 NVIDIA/AMD 张量核上实现 FP64 模拟，cuBLAS 13.x 的 FP64 emulation + ADP 把“自动选参 + 默认精度不低于原生 + 无收益回退”产品化，Intel Arc Xe2 实现 Ozaki-II，Intel AMX/Arm SVE2 也出现 INT8 模拟 FP64 的工作。Matsuoka 2026 的 Ozaki 2.5 / “FP8 is All You Need” 进一步给出 B300/Rubin 上的模型级硬件选项，但作者明确其为 projected floor，没有 RTL/综合证据。

2.3 硬件实现与 OzCore 基线

OzCore 是第一个把 Ozaki-II 做成整数化 GEMM 架构的工作：预处理、模归约、CRT 重构全部整数化，消除 FP64/FP32 辅助运算；用更紧的缩放界减少达到目标精度所需的 INT8 GEMM 次数；用 12 个 CRT slot 支持 s∈{2,3,4,6,12} 的运行时切换；相对 INT8 阵列仅增加 27.9% 面积。在 LLaMA-3.1 8B/70B 上 s=3 匹配 BF16 困惑度，相对融合多格式基线取得 1.91× TOPS/mm²、1.40× TOPS/W。

OzCore 的贡献证明“整数阵列可以统一支持多精度”，但其评估以中大规模 GEMM 为主，未系统回答小/中矩阵的非 GEMM 开销、精度合同/最坏情况保证、N 倍中间平面的数据流，以及同面积原生 FP64/FP32 的公平对照。它的 INT8-only 对自研 ASIC 不是缺陷，而是合理基线；我们的实测也显示 INT8 在 BF16/FP16/FP32/FP64 等精度下面积—能耗最优。

OzCore 的微架构由预处理、INT8 阵列、后处理三部分组成：预处理做缩放、指数感知取模与 8-bit 余数打包；后处理用 12 个 CRT slot 做模归约、加权与 128-bit 累加，支持 s∈{2,3,4,6,12} 的分组重构。其 27.9% 面积开销主要来自前/后处理与 CRT；但论文的评估集中在 8192³ 级 GEMM 与 LLaMA 推理，没有给出 K=1024–4096 的非 GEMM 分解，也没有同面积原生 FP64/FP32 的对照。

2.4 软件与产业实现

GPU 侧，GEMMul8、ozIMMU、cuBLAS 13.x 的 FP64 emulation + ADP、Intel Arc Xe2 的 Ozaki-II 实现，已把“用低精度张量核模拟高精度”产品化。ADP 在库层做“自动选参 + 默认精度不低于原生 + 无收益回退”；Matsuoka 2026 的 Ozaki 2.5 与“FP8 is All You Need”给出 B300/Rubin 上的模型级硬件选项，但作者明确其为 projected floor，没有 RTL/综合证据；Intel 的 US12455722B2 等专利布局了浮点分解电路与动态精度。

这些工作说明“算法可行/产品可用”已不构成新颖性；体系结构的机会在于：把变换/重构做成可综合硬件、给出可证明精度、做同面积公平评估，并交付 CPU+加速器的可运行系统。

在精度控制上，ADP 与 OzCore 的 s 都只是“选参”：ADP 在库层用启发式估计动态范围，OzCore 用 s 寄存器控制重构吞吐；两者都没有把“误差界”作为硬件可执行合同，也没有在最坏输入下提供守卫/回退的 RTL 证据。对科学计算用户，缺少最坏情况保证意味着无法在提交作业前判断结果是否可信。

2.5 精度合同与自适应调度

ADP 在软件层验证了“精度自动选择 + 回退”的可行性，但它是黑盒：应用不能声明最坏情况界，也拿不到逐层误差统计；硬件对 N/算法/缩放无感知。OzCore 的 s 寄存器提供了运行时重构吞吐切换，但没有应用级合同、守卫与统计。现有工作缺少“把精度变成硬件可执行合同”的体系结构抽象。

2.6 同面积评估与系统验证

现有加速比多相对“原生 FP64 DGEMM”或融合多格式基线报告。GPU 厂商的 FP64 单元面积极小，这种比较会系统性高估模拟收益；真正公平的做法是用 a₆₄（FP64 FMA/INT8 MAC 面积比）、a₃₂ 把原生阵列缩放到与统一引擎相同面积，再比较有效吞吐/能效。OzCore 相对融合基线做了公平比较，但没有回答同面积原生 FP64/FP32 的问题。

系统验证方面，Chipyard/Gemmini 提供可复用的 SoC/脉动阵列基础设施，FireSim 可在 Alveo U250 上做周期精确的 FPGA 加速仿真。现有 Ozaki 硬件工作多为综合/模型级评估，缺少 CPU+加速器的端到端系统与精度合同回读。

同面积评估方面，Demmel 等提出的 BLAS 精度分级（A/B/C 与 ungameable tests）为“精度保证”提供了可复现的测试方法；但现有 Ozaki 硬件工作尚未把该方法与 a₆₄/a₃₂ 面积归一化结合。Chipyard/Gemmini 提供了可复用的 SoC 与脉动阵列基础设施，FireSim 可在 U250 上做周期精确的 FPGA 加速仿真；但 Ozaki 硬件工作多停留在综合/模型级，缺少 CPU+加速器的端到端验证。

现有精度控制多为“选参”而非“合同”：ADP 用启发式估计动态范围，OzCore 用 s 寄存器控制重构吞吐；二者都没有把“最坏情况误差界”作为硬件可执行约束，也没有在输入越界/溢出时提供 RTL 级守卫与回退。对科学计算用户，缺少最坏情况保证意味着无法在提交作业前判断结果是否可信；对 LLM 用户，缺少精度统计意味着无法做逐层精度—吞吐权衡。

同面积评估的核心是用 a₆₄（FP64 FMA/INT8 MAC 面积比）、a₃₂ 把原生阵列缩放到与统一引擎相同面积/功耗，再比较有效吞吐与能效；Demmel 等的 BLAS 精度分级（A/B/C + ungameable tests）为“精度保证”提供可复现测试。系统验证方面，Chipyard/Gemmini 提供可复用 SoC/脉动阵列，FireSim 可在 U250 上做周期精确的 FPGA 加速仿真；但现有 Ozaki 硬件工作多停留在综合/模型级，缺少 CPU+加速器的端到端系统与精度合同回读。

文献检索以 Ozaki II、FP8/FP4 emulation、CRT/RNS、multi-precision accelerator、same-area evaluation、Chipyard/FireSim 为关键词，覆盖 2016–2026 年 ISCA/MICRO/HPCA/SC/TCAD/arXiv；阅读方式包括原文精读、开源代码/文档核对，以及与我们前期 RTL/综合数据的对照。

Ozaki I 与 II 的取舍并非绝对：I 的后端只需按切片指数移位与宽定点累加，II 的后端需要 CRT 模归约/加权/宽整数累加；当 K 较小、CRT 后端无法被 GEMM 摊薄时，I 可能更优；当 K 较大、目标精度高时，II 的 GEMM 次数优势更明显。因此本课题默认 II，但保留 I 作为小 K/低精度回退，并在 WP1 用代价模型给出交叉点。

硬件数据流方面，OGE 的前端需要按行/列统计、缩放、取模、打包；中端 INT8 阵列按模数串行复用；后端在每个模数 GEMM 后立即做 mod pᵢ、加权与 128-bit 累加，全部模数完成后 mod P/反缩放/舍入。关键不是单个模块，而是 FTU、阵列、CRT 三者的吞吐匹配与双缓冲：FTU 必须在阵列跑当前模数时生成下一模数平面，CRT 必须在上一个 tile 的 GEMM 结束前完成重构。

评估方面，除吞吐/面积/能耗外，还需报告非 GEMM 开销分解、HBM 流量、SRAM 带宽、精度统计（ulp 分布、正确舍入比例）、以及同面积原生 FP64/FP32 的加速比/能效比；工作负载覆盖 K=1024–16384、LLaMA PPL、HPL trailing update、量子化学 DGEMM 与张量网络收缩，避免只报单一形状的峰值。

本课题的边界是有限、非特殊值的 GEMM；NaN/Inf/带符号零/次正规采用检测+回退，不在低精度流水线内实现完整 IEEE 754 语义；这一边界与 OzCore/现有 Ozaki 实现一致，但需要在精度合同中明确声明。

与 OzCore 相比，本课题的增量不在算法本身，而在工程闭环：OzCore 证明了整数化前/后处理与可重构 CRT 的可行性；本课题进一步把精度合同、最坏情况守卫、小矩阵双缓冲/批处理、同面积 a₆₄/a₃₂ 包络与 Chipyard/FireSim/U250 系统验证串成一条可复现的证据链。这样既能避免与 OzCore/ADP/专利的重复，也能让“统一引擎是否值得做”成为一个可证伪的实验问题。若 M1 的 a₆₄ 低于阈值，本课题将转向 FP32-first 或负结果/测量论文，而不是强行包装加速比。

此外，本文也参考了 OpenROAD/ASAP7 与 TSMC 28 nm 公开库文档，用于面积/能耗口径的统一；所有引用数字均标注来源，避免把不同工艺/口径的数字直接比较。这为后续同面积评估提供可复现的基线。

2.7 研究空白与本课题定位

综上，研究空白可归纳为四点：小/中矩阵非 GEMM 开销、精度合同/最坏情况保证、N 倍中间平面的数据流与存储、同面积原生对照与可运行系统验证。本课题以 OzCore 为基线，主线收敛为 INT8-only + 精度合同 + 小矩阵融合；FP8/FP4 作为 WP6 可选扩展，不作为核心创新；算法族默认 Ozaki II，Ozaki I 作为小 K/低精度回退；最终用 a₆₄/a₃₂ 包络与 Chipyard/FireSim/U250 系统验证给出可辩护结论。

综上，现有工作已经证明“算法可行、整数阵列可实现、软件可产品化”，但尚未回答：小/中矩阵的非 GEMM 开销能否压到 <10%；精度能否作为硬件合同被最坏情况保证；N 倍余数平面能否在片上数据流中不落 HBM；统一引擎在同面积原生 FP64/FP32 下是否真正占优；以及 CPU+加速器系统能否端到端运行。

## 三、研究内容

### 1.研究目标

总体目标：证明“精度虚拟化的 INT8-only Ozaki GEMM 引擎”在同面积、同功耗、可证明精度的约束下，相对原生 FP64/FP32 与 OzCore 具有可辩护的 Pareto 优势，并交付可综合、可复现的原型。

L1 模型与算法：精度—代价—面积—能耗模型；Ozaki I/II 交叉规则；三基 pass 数复核；目标工艺 a₆₄/a₃₂ 综合标定。验收：复现文献 ≥80% 数字；给出目标工艺的 Go/No-Go。

L2 架构与仿真：OGE 架构规格；周期级模拟器；精度合同 API；DSE 结果。验收：模拟器 vs RTL 误差 <5%；K=1024–4096 非 GEMM 开销 <10%。

L3 原型与系统：可综合 RTL；综合面积/功耗；Chipyard/FireSim/U250 的 CPU+加速器系统；软件栈。验收：全配置对 MPFR 黄金模型；a₆₄≥30 时 FP64 ≥1.5×，否则 ≥1.0× 且能效 ≥2×；FPGA 端到端应用可运行。

### 2.主要研究内容、需要解决的关键理论问题或技术问题

（1）精度虚拟化与硬件合同（I1）：定义 EXACT/BOUNDED/FAST 三级合同；缩放上界 vs P/2、重构后范围检查、越界增大 N 或回退；ulp 分布/正确舍入比例/实际 N 统计回读；合同跨 INT8/FP32/FP64 与 I/II 算法族生效。关键问题：最坏情况误差界的构造性证明、守卫的完备性、合同与吞吐的在线权衡。

（2）小矩阵非 GEMM 开销压缩（I2，核心）：FTU（尺度不变缩放、指数感知取模、limb 编码、TN 布局）+ CRT epilogue（mod pᵢ、加权、128-bit 累加、mod P、反缩放/舍入）+ 余数平面双缓冲 + 自适应 N/算法/分块 + 批处理/持久化 kernel。关键问题：FTU 吞吐与阵列匹配、CRT 后端与 GEMM 的重叠、K=1024–4096 时非 GEMM 开销 <10%、精度合同驱动的 N 选择。

（3）存储/数据流协同（I3）：余数平面片上双缓冲；tile（128×128 输出）与 k-block（64–128）；SRAM 容量/带宽与 tile 调度；HBM 流量不随 N 线性增长；小矩阵 batch/流式与子阵列并行。关键问题：低算术强度下的数据复用、片上缓冲深度与面积/带宽的权衡、N 与 HBM 流量解耦。

（4）同面积评估 + FPGA 系统验证（I4）：综合 INT8/FP32/FP64 MAC 与阵列，标定 a₆₄/a₃₂/e₆₄/e₃₂；同面积/同功耗/同带宽/同精度归一化；可行性包络与 Go/No-Go；Chipyard + FireSim/Alveo U250 的 Rocket/BOOM + OGE SoC；U250 用 32×32/16×16 缩比阵列，全尺寸用 FireSim/ASIC 综合；端到端应用与精度统计回读。关键问题：原生阵列缩放口径、FPGA 资源/时序、系统级收益与 kernel 级收益的区分。

（5）工作包：WP1 模型/算法规则/a₆₄ 标定；WP2 小矩阵融合微架构/模拟器；WP3 精度合同/守卫；WP4 RTL（FTU/CRT/接口）；WP5 软件/ Chipyard/FireSim/U250/应用/同面积；WP6 可选多基/多字/复矩阵扩展。

### 3.工作方案（研究方法、技术路线等）及可行性分析

技术路线：模型 → 模拟 → RTL → FPGA/系统四条线迭代。先用 Python 建立精度—代价—面积—能耗模型，复现文献数字并给出 a₆₄/a₃₂ 相图/Go-No-Go；再用周期级模拟器验证小矩阵数据流、双缓冲、N/算法/分块；随后实现 FTU、CRT 后端、守卫与 INT8 阵列接口，用 Verilator 对 MPFR 黄金模型；最后用 Chipyard + FireSim/U250 搭 CPU+OGE 系统，跑 BLAS 风格库与 1–2 个应用，做同面积/端到端评估。

OGE 数据流：A/B tile → FTU 生成余数平面 → INT8 阵列逐模数 GEMM → epilogue 立即 mod/加权/128-bit 累加 → 全部模数完成后 mod P/反缩放/舍入 → 写回 C；余数平面双缓冲，FTU(i+1) 与 GEMM(i)、CRT(t-1) 与 GEMM(t) 重叠。主阵列 INT8-only；FP8/FP4 仅 WP6 可选；算法族默认 II，I 作小 K/低精度回退。

可行性：① 算法侧已有 Ozaki II/FP8/FP4/fast scaling 四篇论文与我们的位预算/数值仿真，三基 pass 数已复核；② 硬件侧已有 P0/P0b INT8 MAC 与 128×128 阵列实测：TSMC 28 nm HPC+ FF 下 INT8 378.13 µm²/0.366 pJ，阵列 5.903 mm²/1.800 W（8×8 tile 实测 + 256 tile 组合），FP8/FP4 也已完成综合对照；③ EDA 侧有 DC/VCS/TSMC 28 nm 与开源 ASAP7/OpenROAD 备选；④ 系统侧有 Chipyard/Gemmini/FireSim 开源基础设施与 Alveo U250；⑤ 风险可控：a₆₄ 不足则转 FP32-first/能效/负结果论文，RTL 工期紧则关键模块优先，FPGA 资源不足则用缩比阵列 + FireSim 全尺寸。

### 4.创新性

I1 精度合同：相对 OzCore 的 s 寄存器，增加应用级 EXACT/BOUNDED/FAST 语义、最坏情况守卫、跨精度/算法族的统计回读；把“精度”从隐式参数变成可验证合同。

I2 小矩阵非 GEMM 开销压缩：以 K=1024–4096 的困难区间为目标，用指数感知 FTU、CRT epilogue、余数平面双缓冲、自适应 N/算法/分块、批处理/持久化 kernel，把非 GEMM 开销从 27–55% 压到 <10%，有效吞吐相对 GPU 软件模拟 ≥2×；OzCore 以中大规模 GEMM 为主，未系统解决该区间。

I3 存储/数据流协同：余数平面片上双缓冲、tile/K-block、SRAM 带宽/容量协同，使 HBM 流量不随 N 线性增长；相对 OzCore 的 tile 级 pre/post，补充小矩阵低算术强度的数据流设计。

I4 同面积 + 系统验证：用目标工艺 a₆₄/a₃₂ 标定与同面积/同功耗/同带宽包络，补 OzCore 缺失的“原生 FP64/FP32”一维；用 Chipyard/FireSim/U250 做 CPU+加速器端到端验证，把 kernel 级结论推进到系统级。

说明：不使用“首个/首次”作为无条件表述；所有“首次”限定在“据我们所知 + 可综合 RTL + 同面积/系统证据”的组合上。多基不作为核心新颖性主张；算法族选择作为 WP1 的次要规则。

## 四、研究条件

已具备条件：① 文献与算法基础：Ozaki II、FP8/FP4 变体、fast scaling、OzCore 四篇核心论文已精读，完成三基 pass 数复核与数值仿真；② 硬件/EDA：TSMC 28 nm HPC+ FF 库、Synopsys DC/VCS、P0/P0b INT8 MAC 与 128×128 阵列的综合/功耗数据；③ 计算资源：Python/C++ 模型、Linux 服务器、8 GB EDA VM（可扩内存）、Alveo U250 与 Chipyard/FireSim 开源基础设施（计划）；④ 团队/导师：体系结构、数值分析、EDA 方向可获指导；⑤ 前期结果：INT8 MAC 378.13 µm²/0.366 pJ、阵列 5.903 mm²/1.800 W；FP8/FP4 MAC/阵列对照；等精度成本 INT8 最优。

可能遇到的困难与解决措施：① a₆₄/a₃₂ 目标工艺综合不确定——先用 ASAP7/OpenROAD 与 TSMC 28 nm 双口径，给出区间包络；若低于阈值，转 FP32-first/能效/负结果论文（Plan B）。② RTL 工期紧——关键模块优先（FTU/CRT/守卫），系统集成后置，复用 Gemmini/Chipyard 接口。③ 精度证明难——限定有限非特殊值，特殊值回退；差分测试 + 形式化守卫；与数值分析合作。④ FPGA 资源不足——U250 用 32×32/16×16 缩比阵列验证系统，全尺寸用 FireSim/ASIC 综合；提前做资源估算。⑤ 非 GEMM 开销压不下——调整 tile/双缓冲/子阵列，必要时把主战场移到大规模并诚实报告。
