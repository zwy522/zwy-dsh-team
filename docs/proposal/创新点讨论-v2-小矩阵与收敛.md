# 创新点讨论 v2：算法族收敛、物理基收敛与小矩阵重点

> 回应四点反馈：① Ozaki II 是否总优于 I；② INT8 已验证最优，FP8/FP4 是否还要做；③ 第 3 点可行；④ 增加 Chipyard + FireSim/U250 的 FPGA 系统验证；并把“小矩阵非 GEMM 开销压缩”作为创新点展开重点。

## 1. Ozaki II 是否总优于 Ozaki I？

**结论：不是。** 不能把“II 一定优于 I”作为前提；但算法族选择可以从“核心创新”降为 WP1 的**次要选型规则**，不必单独占一个创新点。

一阶对比（INT8 基，b_s≈8 bit/片，N 为 II 的模数）：

| 目标 | I 的切片数 k | I 的 GEMM（fast, k(k+1)/2） | II 的 GEMM（N） | GEMM 较少者 |
|---|---:|---:|---:|---|
| BF16 (B=8) | 1–2 | 1–3 | 4 | **I** |
| FP16 (B=11) | 2–3 | 3–6 | 4 | I 或 II（接近） |
| FP32 (B=24) | 3–4 | 6–10 | 8 | II（k=4 时 10） |
| FP64 (B=53) | 7–8 | 28–36 | 14–16 | **II** |

但 GEMM 次数不是全部：II 的 CRT 后端更重（宽整数、模 P、加权），I 的后端只是移位 + 宽定点累加。**当 K 较小、输出规模较小、CRT 后端无法被 GEMM 摊薄时，I 可能反超 II**；动态范围极端时，II 的模数乘积/缩放约束也可能需要更多模数。反过来，K 大、目标精度高时，II 的 GEMM 次数优势会压倒后端开销。

因此：
- **不能**声明“所有形状/精度/动态范围下 II 都优”；
- 但也不需要把“算法族选择”做成核心创新：在 WP1 的代价模型里加一条 **I/II 交叉规则**（按 K、B、动态范围、CRT 面积比选择），作为运行时启发式的一部分即可；
- 如果博士主线锁定 **FP64/FP32 + 中大规模 K**，II 有明确优势，可以默认 II，把 I 作为小 K/低精度回退路径。

**建议**：保留 I/II 双映射（共享前端/阵列，后端可配置），但把“算法族选择”写成 WP1 的**一条规则**，不单独作为创新点。

## 2. INT8 已验证最优，FP8/FP4 还有必要吗？

**结论：对“自研 ASIC + 高精度统一模拟”这条主线，没有必要把 FP8/FP4 作为核心创新。** 建议：

- 主线 **INT8-only**：我们的实测（TSMC 28 nm HPC+ FF）显示 INT8 在 BF16/FP16/FP32/FP64 等精度下都是面积—能耗最优；FP8/FP4 MAC 为 INT8 的 1.46–1.64× 面积，阵列 1.63–1.82×；多基只会增加面积/复杂度，除非有明确的原生低精度负载。
- FP8/FP4 降为 **可选扩展（WP6）**：只在两种情况下启动：
  1. 目标平台是**他人给定的 GPU/加速器**，峰值比不可设计，且 INT8 峰值被削减；
  2. 系统需要**原生 FP8/FP4 低精度模式**（LLM 推理），而不是用 INT8 模拟。
- 若主线是自研 ASIC，**INT8-only 的统一阵列 + 精度合同 + 小矩阵融合**是更聚焦、更有说服力的博士题目；多基可以作为博士论文的“扩展章节”或后续工作。

这样也解决了 I2 当前的弱点：不再用“平台峰值比”为多基辩护，而是把创新点集中到小矩阵/非 GEMM 开销。

## 3. 小矩阵“困难”与非 GEMM 开销：创新点展开

### 3.1 为什么小矩阵难

设 GEMM 为 m=n=K=1024–4096。非 GEMM 工作量约 O(N·mn)（变换、取模、CRT 重构），GEMM 为 O(N·mnK)。非 GEMM 占比大致按 1/K 增长；K 从 8192 降到 1024，占比约升 8×。再加上：
- kernel launch / 流水填充 / tile 边界；
- N 个余数平面的片上/片外往返；
- CRT 后端的宽整数操作无法与 GEMM 完全重叠；
- 小矩阵并行度不足，阵列利用率下降。

软件实现中该占比 27–55%，这正是小矩阵的“困难区间”。

### 3.2 四条压缩路径

1. **前端融合（FTU）**：尺度不变缩放 + 指数感知取模，避免物化 110-bit 整数；按行/列统计在 DMA 中顺带完成；limb 编码流水化。目标：FTU 吞吐 ≥ 阵列每周期操作数需求，不成为瓶颈。
2. **后端融合（CRT epilogue）**：每个模数 GEMM 完成后立即做 mod pᵢ、加权乘加、128-bit 累加；全部模数完成后统一 mod P/反缩放/舍入；中间结果不落 HBM。
3. **双缓冲与重叠**：余数平面双缓冲；FTU(i+1) 与 GEMM(i) 重叠；CRT(t-1) 与 GEMM(t) 重叠；用 tile 级流水把后端藏到 GEMM 后面。
4. **自适应 N/算法/分块**：用精度合同（BOUNDED/FAST）减少小矩阵的 N；按 K/B/动态范围在 I 与 II 之间切换；K-block 与 batch 让阵列保持高利用；对小矩阵做批处理/持久化 kernel，摊薄启动与填充。

### 3.3 量化目标

- 1024–4096 的“困难区间”：非 GEMM 开销从 27–55% 压到 **<10%**；
- 有效吞吐相对 GPU 软件模拟 **≥2×**；
- HBM 流量不随 N 线性增长（只与 tile 数相关）；
- 精度合同可验证（EXACT/BOUNDED 的误差统计与 MPFR 一致）。

### 3.4 与 OzCore 的差异（需要核实）

OzCore 已有三阶段全流水 pre/post，且 pipeline fill 相对 GEMM tile 可忽略；因此“无 HBM 中间矩阵”不能直接当作独有增量。需要逐条对照其数据流，明确我们的差异在：
- 指数感知取模 / 尺度不变缩放的**前端微架构**；
- 多模数 **CRT epilogue 与双缓冲**的 tile 级调度；
- **小矩阵**（K=1024–4096）的 N/算法/分块自适应与批处理；
- 精度合同驱动的 N 选择（避免为小矩阵过度配置）。

## 4. 修订后的创新点结构（建议）

| 编号 | 创新点 | 相对 OzCore 的增量 | 验证 |
|---|---|---|---|
| I1 | 精度合同与硬件守卫 | 应用级 EXACT/BOUNDED/FAST + 最坏情况守卫 + 统计回读；OzCore 只有 s 寄存器 | 对抗输入、契约吞吐差、MPFR 统计 |
| I2 | 小矩阵非 GEMM 开销压缩（核心） | FTU + CRT epilogue + 双缓冲 + 自适应 N/算法/分块；目标 <10% | 1024–4096 非 GEMM 占比、有效吞吐 |
| I3 | 存储/数据流协同 | 余数平面片上双缓冲、tile/K-block、批处理；避免 N 倍 HBM | HBM 流量、SRAM 带宽、阵列利用率 |
| I4 | 同面积评估 + FPGA/FireSim 系统验证 | a₆₄/a₃₂ 标定 + 同面积包络 + Chipyard/FireSim/U250 可运行系统 | a₆₄ 曲线、端到端应用、FPGA demo |

说明：
- 原 I2（多基）降为 WP6 可选扩展；
- 原 I3（端到端融合）与 I2（小矩阵）合并/重排，避免“融合”与“小矩阵”两个宽泛概念重叠；
- I3 也可以并入 I2，形成“三条核心 + 一条评估”的结构；建议按上表保留四条，便于论文拆分。

## 5. FPGA 原型系统验证（Chipyard + FireSim/U250）

按反馈加入系统级验证：

- **平台**：Chipyard 生成 Rocket/BOOM CPU + OGE 加速器的 SoC；FireSim 在 Alveo U250 上做周期精确的 FPGA 加速仿真；运行 BLAS 风格库与 1–2 个应用 kernel。
- **规模**：U250 资源（约 2.7M LUT、9k DSP、38 MB BRAM）难以放下完整 128×128 INT8 阵列（16K MAC）；采用 **32×32 或 16×16 的缩比阵列**做 FPGA 原型，验证 CPU+加速器系统、驱动、精度合同与端到端流程；完整 128×128 用 FireSim/ASIC 综合评估。
- **验证内容**：CPU 发起 `oge_gemm` → 驱动/队列 → OGE 执行 → 精度统计回读；与 MPFR/GPU 对比；测端到端延迟、吞吐、非 GEMM 开销；跑一个真实应用（如 HPL trailing update 或量子化学 DGEMM）。
- **里程碑**：M5（第 27–33 月）完成 FPGA 原型与端到端结果；M6 整合进论文/artifact。
- **风险**：U250 资源/时序；FireSim 编译时间；缩比阵列与全尺寸的性能外推需标定。
