## 摘要

大模型与科学计算同时要求 FP64/FP32/FP16/BF16/FP8/FP4/INT8 等多精度 GEMM，而芯片面积与功耗越来越向低精度倾斜。Ozaki Scheme II 把高精度矩阵乘分解为若干次精确整数矩阵乘，再用中国剩余定理（CRT）重构，为“单一低精度阵列支持多精度”提供了数学基础。OzCore（MICRO 2026）把该方案做成整数化的 GEMM 架构：在 INT8 阵列上增加 27.9% 的前/后处理面积，即可在 LLaMA-3.1 上匹配 BF16 困惑度，并相对融合多格式基线取得 1.91× TOPS/mm² 与 1.40× TOPS/W。

OzCore 证明了“整数阵列可以统一支持多精度”，但留下三个工程问题：其一，小/中矩阵（K=1024–4096）的非 GEMM 开销占 27–55%，CRT 与分解无法被 GEMM 充分摊薄；其二，精度由分解次数隐式决定，缺少应用级精度合同、最坏情况守卫与可观测统计；其三，N 倍余数平面带来存储/带宽压力，且缺少“同面积原生 FP64/FP32”的公平对照与可运行系统验证。我们的前期实测进一步表明：在自研 28 nm ASIC 上，INT8 在 BF16/FP16/FP32/FP64 等精度下都是面积—能耗最优，FP8/FP4 多基并不是高精度模拟的必需项；因此本课题把主线收敛为 **INT8-only + 精度合同 + 小矩阵融合**。

本课题提出 **OGE（Ozaki GEMM Engine）**：以 INT8 精确阵列为主算力，向前融合尺度不变缩放、指数感知取模，向后融合宽整数 CRT 重构与正确舍入；以 **精度虚拟化** 把目标格式、误差界与动态范围变成可调度、可验证的硬件合同；以 **小矩阵非 GEMM 开销压缩** 为核心，用 FTU/CRT epilogue/双缓冲/自适应 N 与分块把 1024–4096 的困难区间压到 <10%；以 **同面积可行性包络 + Chipyard/FireSim/U250 系统验证** 回答“统一引擎在什么条件下真正占优”。课题按博士 36 个月规划，设置 M0–M6 里程碑，以模型—模拟—RTL—系统四条线迭代，预期形成可综合 RTL、周期级模拟器、精度合同 API、FPGA 原型与 2–3 篇高水平论文。

**关键词**：多精度计算；Ozaki Scheme II；GEMM；精度虚拟化；CRT 重构；加速器体系结构；同面积评估

## 第 1 章 绪论

### 1.1 研究背景与意义

过去十年，矩阵引擎的峰值算力持续向低精度迁移。以公开规格为例，A100 的 INT8 峰值约为 FP64 的 64 倍，RTX 4090 达到 512 倍，B200 为 122 倍；面向 AI 的 B300 把 INT8 削减到约 150 TOPS、FP64 仅约 1.2 TFLOPS，同时把 FP4 提升到 14 PFLOPS 量级；Rubin 一代延续该趋势。与此同时，HPC 与科学计算仍依赖 FP64， LLM 训练/推理则混合使用 BF16、FP8、FP4 与 INT8。**精度碎片化** 与 **FP64 算力危机** 成为体系结构必须同时面对的两个事实。

传统方案是数据通路融合（datapath fusion）：在一个 MAC 中复用乘法器、符号/指数/累加逻辑，支持多种格式。但每增加一种格式，就增加一份在大多数时间空闲的硬件，持续稀释单位面积算力。另一条路线是领域专用：只做一种格式，牺牲灵活性与互操作性。Ozaki 方案给出了第三条路：**用低精度整数运算模拟高精度浮点**，精度由分解次数而不是数据通路决定。

Ozaki Scheme II 将浮点矩阵按行/列共享指数缩放为整数，对一组两两互素的模数取余，在低精度阵列上做精确整数 GEMM，再用 CRT 恢复整数乘积并反缩放。其关键性质是：中间乘积精确、误差可分析、GEMM 次数随模数个数线性增长。FP8 变体把每个模数压缩为 3 次 FP8 GEMM；FP4 base-13 变体利用 E2M1 “加倍后为整数”的性质，用 19 个模数、75 次 FP4 GEMM 达到 FP64。

OzCore 是这一路线在体系结构层面的标志性工作。它把预处理、模归约与 CRT 重构全部整数化，消除了对 FP64/FP32 辅助运算的依赖；用更紧的缩放界减少达到目标精度所需的 INT8 GEMM 次数；用可重构 CRT 单元支持 s∈{2,3,4,6,12} 的运行时切换。其结果显示：在 128×128 INT8 阵列上仅增加 27.9% 面积，即可在 LLaMA-3.1 8B/70B 上匹配 BF16 困惑度，并在等精度下相对融合多格式基线取得 1.91× TOPS/mm² 与 1.40× TOPS/W。

OzCore 证明了“统一整数阵列”的可行性，但也把问题推进到下一层：**当基准从“融合多格式”换成“原生 FP64/FP32 + 独立低精度单元”时，统一引擎是否仍然占优？当平台从 INT8 峰值充裕的 B200 换到 INT8 被削减的 B300/Rubin 时，单一 INT8 基是否仍然最优？当矩阵从 8192³ 缩小到 1024–4096 的“困难区间”时，非 GEMM 开销与中间平面存储是否会吞掉收益？** 这些问题不解决，“统一”就只是一个漂亮的架构口号，而不是可辩护的博士课题。

### 1.2 国内外研究现状

**算法侧。** Ozaki I 沿尾数切片，GEMM 次数随切片数平方增长；Ozaki II 用 CRT，GEMM 次数随模数线性增长，是当前高精度模拟的主流。2026 年的三项进展进一步完善了工程可用性：FP8 量化版用 3 次 FP8 GEMM/模数、12–13 个模数达到 FP64；FP4 base-13 版用 19 个模数、75 次 FP4 GEMM；fast-mode 缩放改进指出现有 fast 公式缺乏尺度不变性，并给出零额外开销的修正。软件实现方面，GEMMul8、ozIMMU、cuBLAS 13.x 的 FP64 emulation + ADP、Intel Arc Xe2 的 Ozaki-II 实现，已经把“算法可行”推进到“产品可用”。

**硬件侧。** OzCore 是第一个把 Ozaki-II 做成整数化 GEMM 架构的工作；此前的多精度阵列（Bitfusion、Stripes、BitWave、Laconic、UNPU 等）主要做格式级可重构或位串行，不改变 MAC 的精度语义；RNS/CRT 加速器多用于密码与信号处理，未与 Ozaki 的缩放/重构闭环结合。Matsuoka 2026 的 Ozaki 2.5 与 “FP8 is All You Need” 给出了 B300/Rubin 上的模型级硬件选项，但作者明确其为 projected floor，没有 RTL/综合证据；Intel 的 US12455722B2 等专利布局了浮点分解电路与动态精度，说明“把高精度拆成低精度”本身已不再是新颖性来源。

**评估侧。** 现有工作的加速比大多相对“原生 FP64 DGEMM”报告，但 GPU 厂商的 FP64 单元面积极小，这种比较会系统性高估模拟的收益。真正公平的做法是 **同面积/同功耗/同带宽/同精度保证** 的归一化：用 a₆₄（FP64 FMA 面积 / INT8 MAC 面积）、a₃₂ 把原生阵列缩放到与统一引擎相同面积，再比较有效吞吐与能效。OzCore 相对融合多格式基线做了公平比较，但没有回答“相对同面积原生 FP64/FP32”的问题。

### 1.3 现有工作的不足与本课题的切入点

**不足 1：小/中矩阵的非 GEMM 开销。** 软件实现中，量化、取模、CRT 重构在小/中矩阵上占 27–55%；K 从 8192 降到 1024，非 GEMM 占比约升 8×。OzCore 已把前/后处理整数化并流水，但未系统回答“K=1024–4096 时如何把 CRT/分解藏到 GEMM 后面、把开销压到 <10%”。

**不足 2：精度是隐式的，不是合同。** OzCore 用 s 控制精度，s 是运行时寄存器；但应用只能选 s，不能声明“正确舍入 / ≤2 ulp / 容差 ε”，也拿不到最坏情况保证与逐层误差统计。对科学计算用户，“精度可证明”比“平均误差小”更重要。

**不足 3：N 倍中间平面与存储/带宽。** N 个余数平面使工作内存随 N 线性增长；小矩阵上，SRAM 容量/带宽与 tile 调度更容易成为瓶颈。需要端到端的数据流与存储协同，而不是只优化 GEMM 内核。

**不足 4：同面积对照与可运行系统验证。** 现有加速比多相对“原生 FP64 DGEMM”或融合基线；缺少 a₆₄/a₃₂ 的目标工艺标定、同面积/同功耗包络，以及 CPU+加速器的可运行系统验证（Chipyard/FireSim/U250）。

**关于物理基的说明**：OzCore 的 INT8-only 对“自研 ASIC + 高精度模拟”不是缺陷，而是合理基线。我们的实测（TSMC 28 nm HPC+ FF）显示 INT8 在 BF16/FP16/FP32/FP64 等精度下面积—能耗最优；FP8/FP4 MAC 为 INT8 的 1.46–1.64×，阵列 1.63–1.82×。因此本课题主线保持 INT8-only，把 FP8/FP4 作为 WP6 可选扩展（面向“平台峰值比不可设计”或“原生低精度模式”），不把多基作为核心创新。

### 1.4 研究问题

- **RQ1（选型）**：给定工艺面积比 a₆₄/a₃₂、矩阵形状、目标精度与动态范围，如何联合选择算法族（Ozaki I/II）、物理基（INT8/FP8/FP4）、模数/limb 数 N、缩放模式与分块，使“计算 + 变换 + 重构 + 存储”的总代价最小？
- **RQ2（微架构）**：前端变换、余数平面、阵列、CRT 后端如何流水与双缓冲，才能在小/中矩阵上把非 GEMM 开销压到 10% 以下，并把中间结果留在片上？
- **RQ3（精度保证）**：如何用硬件合同、唯一性守卫与精度统计，保证最坏输入下的误差界，并在精度与吞吐之间做运行时权衡？
- **RQ4（系统价值）**：在同面积/同功耗/同带宽/同精度保证下，OGE 相对原生 FP64/FP32、OzCore、GPU 软件模拟的 Pareto 优势区间在哪里？

### 1.5 研究内容与贡献概述

本课题围绕四个创新点展开（详见第 3 章）：

1. **I1 精度虚拟化与硬件合同**：把目标格式、误差界、动态范围变成可调度、可验证的合同；硬件自动选择 N/缩放/分块，并用守卫与统计保证合同。相对 OzCore 的 s 寄存器，增加应用级语义、最坏情况守卫与可回读精度统计。
2. **I2 小矩阵非 GEMM 开销压缩（核心）**：FTU（尺度不变缩放、指数感知取模）+ CRT epilogue + 余数平面双缓冲 + 自适应 N/算法/分块 + 批处理/持久化 kernel，把 1024–4096 的非 GEMM 开销从 27–55% 压到 <10%，有效吞吐相对 GPU 软件模拟 ≥2×。
3. **I3 存储/数据流协同**：余数平面片上双缓冲、tile/K-block、SRAM 带宽与容量协同、HBM 流量不随 N 线性增长；为小矩阵的“低算术强度”设计数据流，而不是只做 GEMM 内核优化。
4. **I4 同面积包络 + FPGA 系统验证**：综合 a₆₄/a₃₂/e₆₄/e₃₂，建立同面积/同功耗/同带宽/同精度保证的对比框架；用 Chipyard + FireSim/U250 搭 CPU+OGE 的可运行系统，验证端到端收益、精度合同与软件栈。

## 第 2 章 技术基础与 OzCore 基线

### 2.1 Ozaki Scheme II 与 CRT

给定 FP 矩阵 A∈R^{m×k}、B∈R^{k×n}，Ozaki II 分四步：

1. **缩放**：用 2 的幂行/列缩放 D、E 把 A、B 截断为整数 A′=trunc(D·A)、B′=trunc(B·E)，使整数乘积落在 CRT 可表示范围内；
2. **模分解**：选两两互素模数 p₁…p_N，对每个模数取对称余数 A′ᵢ=A′ mod pᵢ、B′ᵢ=B′ mod pᵢ；
3. **整数 GEMM**：在低精度阵列上计算 C′ᵢ=A′ᵢB′ᵢ；对 INT8 基，内维 q<2¹⁷ 时 INT32 累加精确；
4. **CRT 重构**：C′ ≡ Σᵢ C′ᵢ·(P/pᵢ)·yᵢ (mod P)，P=∏pᵢ；再反缩放并舍入到目标格式。

达到目标有效位 b 所需的模数/GEMM 次数由 CRT 容量与内维决定。对于 FP64（b=53），INT8 基约需 14–16 个模数（容量/工程口径），FP8 基约 12–13 个模数（每模数 3 次 GEMM，36–39 次），FP4 base-13 基 19 个模数（75 次 GEMM）。本课题前期用位预算 + 数值仿真复核了这些数字（附录 A）。

### 2.2 三种物理基的代价

| 基 | 每模数位数 | GEMM/模数 | FP64 模数 / GEMM | 特点 |
|---|---:|---:|---:|---|
| INT8 | 8 | 1 | 14–16 / 14–16 | 有效位/GEMM 最高；阵列最成熟 |
| FP8 E4M3 | 9 | 3 | 12–13 / 36–39 | 单次峰值高，但每模数 3 次 GEMM |
| FP4 E2M1 | ~6.05 | ~3.95 | 19 / 75 | 单次峰值最高，但分解次数最多 |

“哪个基最优”不是固定常数：它取决于目标精度、矩阵形状、非 GEMM 开销，以及平台的低精度峰值比。B200 上 INT8 峰值充裕，INT8 基占优；B300/Rubin 上 INT8 被削减，FP8/FP4 基可能反超。**本课题的主线选择**：在自研 ASIC、以高精度模拟为主要目标的设定下，我们的实测显示 INT8 在 BF16/FP16/FP32/FP64 等精度下都是面积—能耗最优；FP8/FP4 的峰值优势不足以抵消其面积与分解开销。因此主线采用 **INT8-only**，FP8/FP4 作为 WP6 可选扩展；多基不作为核心创新。

### 2.3 OzCore 基线

OzCore 的核心贡献可归纳为四点：

1. **全整数化 Ozaki-II 流水线**：预处理、模归约、CRT 重构都不再依赖 FP64/FP32，显著降低控制逻辑面积；
2. **更紧的缩放界**：减少输入预处理阶段的尾数截断误差，从而减少达到目标精度所需的 INT8 GEMM 次数；
3. **INT8 GEMM 引擎 + 可重构 CRT**：12 个 CRT slot，支持 s∈{2,3,4,6,12} 的运行时切换；相对 INT8 阵列仅增加 27.9% 前/后处理面积；
4. **等精度评估**：相对融合 FP16/BF16/FP8/INT8 的多格式基线，取得 1.91× TOPS/mm²、1.40× TOPS/W；在 LLaMA-3.1 8B/70B 上 s=3 匹配 BF16 困惑度。

OzCore 已经回答了“整数阵列能不能统一支持多精度”，但没有回答本课题的四个问题：小矩阵非 GEMM 开销、精度合同、存储/数据流、同面积原生对照与系统验证。因此本课题把 OzCore 作为**必须逐条对比的基线**，而不是重复实现。

### 2.3.1 与 OzCore 的逐项对比

| 维度 | OzCore（基线） | 本课题（OGE） | 增量/验证 |
|---|---|---|---|
| 物理基 | INT8-only | **INT8-only 主线**；FP8/FP4 为 WP6 可选 | 自研 ASIC 上 INT8 等精度最优；多基不占核心 |
| 精度控制 | s∈{2,3,4,6,12} 运行时寄存器 | EXACT/BOUNDED/FAST 三级合同 + 守卫 + 统计 | 应用级误差界、最坏情况保证、可回读 |
| 小/中矩阵 | 前/后处理流水，但未系统优化 K=1024–4096 | I2：非 GEMM 开销 <10%，有效吞吐 ≥2× | 困难区间实测/模拟 |
| 存储/数据流 | tile 级 pre/post | I3：余数平面片上双缓冲、HBM 不随 N 线性 | HBM 流量、SRAM 带宽、利用率 |
| 算法族 | 固定 Ozaki II + s 调精度 | 默认 II；I 作小 K/低精度回退（WP1 规则） | 交叉点模型，不作为独立创新 |
| 评估 | 相对融合多格式基线 | 同面积/同功耗/同带宽 + 原生 FP64/FP32 | a₆₄/a₃₂ 综合标定 + 可行性包络 |
| 系统验证 | 无 CPU+加速器原型 | Chipyard + FireSim/U250（缩比阵列） | 端到端应用、精度统计、软件栈 |

### 2.4 同面积评估与 a₆₄/a₃₂

设 A_INT8 为单个 INT8 MAC 面积，A_FP64 为单个 FP64 FMA 面积，a₆₄=A_FP64/A_INT8。若 OGE 用 N 次 INT8 GEMM 模拟 FP64，非 GEMM 开销占比 η，则同面积下 OGE 相对原生 FP64 的加速比近似：

```
Speedup_FP64 ≈ a₆₄ / [N × (1 + η)]
```

只有 a₆₄ > N(1+η) 时，统一引擎才在“纯计算面积”上占优。N=14–16、η=10–30% 时阈值约 17–25。类似地，FP32 的阈值 a₃₂ > 7(1+η) ≈ 8–11。ozCore 的实测 INT8 MAC 为 265.4 µm²/MAC；本课题前期在 TSMC 28 nm HPC+ FF 上测得 378.13 µm²/MAC（1.42×），说明工艺/实现差异会显著影响 a₆₄。**a₆₄/a₃₂ 必须用目标工艺综合标定，不能引用文献估计。**

## 第 3 章 研究目标、创新点与关键技术

### 3.1 总体目标

证明“精度虚拟化的统一 Ozaki GEMM 引擎”在同面积、同功耗、可证明精度的约束下，相对原生 FP64/FP32 与 OzCore 具有可辩护的 Pareto 优势，并交付可综合、可复现的原型。目标分三层：

| 层次 | 交付物 | 验收标准 |
|---|---|---|
| L1 模型与算法 | 精度—代价—面积—能耗模型；三基 DSE；相图 | 复现文献 ≥80% 数字；给出目标工艺的 Go/No-Go |
| L2 架构与仿真 | OGE 规格；周期级模拟器；精度合同 API | 模拟器 vs RTL 误差 <5%；小/中矩阵非 GEMM 开销 <10% |
| L3 原型与评估 | 可综合 RTL；综合面积/功耗；软件栈；应用 demo | 全配置对 MPFR 黄金模型；a₆₄≥30 时 FP64 ≥1.5×，否则 ≥1.0× 且能效 ≥2× |

### 3.2 创新点 I1：精度虚拟化与硬件合同

**OzCore 已有什么**：s 是运行时寄存器，支持 {2,3,4,6,12} 的重构吞吐切换；但没有应用级精度语义、没有最坏情况守卫、没有逐层误差统计。

**本文新增什么**：

- 定义三级精度合同：`EXACT`（对缩放后整数输入精确、最终一次正确舍入）、`BOUNDED(ε)`（相对误差 ≤ε，可少用模数/快速缩放）、`FAST`（固定 N，用于迭代求解器内部）；
- 硬件根据合同、动态范围与矩阵形状自动选择算法族/基/N/缩放/分块；
- 唯一性守卫：缩放后用平方和/下采样估计上界并与 P/2 比较；重构后检查符号与范围；越界自动增大 N 或回退；
- 精度统计回读：ulp 分布、正确舍入比例、实际使用的 N/基/缩放模式；
- 应用可根据统计决定是否重算，形成“合同—执行—验证”的闭环。

**与 OzCore 的差异**：把“选 s”升级为“声明误差界 + 硬件保证 + 可观测统计”，并让同一合同跨 INT8/FP8/FP4 基生效。**验证**：同一 DGEMM 在 EXACT 与 BOUNDED(2 ulp) 下应有 ≥1.5× 吞吐差，且统计可被应用读取；对抗输入下守卫必须触发并安全回退。

### 3.3 创新点 I2：小矩阵非 GEMM 开销压缩（核心）

**OzCore 已有什么**：三阶段流水线（preprocess → INT8 GEMM → postprocess），前/后处理全流水，pipeline fill 相对 GEMM tile 可忽略；但其评估以中大规模 GEMM 为主，未系统处理 K=1024–4096 的“困难区间”。

**问题**：非 GEMM 工作量约 O(N·mn)（变换、取模、CRT 重构），GEMM 为 O(N·mnK)；K 从 8192 降到 1024，非 GEMM 占比约升 8×。软件实现中该占比 27–55%。小矩阵还叠加 kernel launch、流水填充、tile 边界、阵列并行度不足、CRT 后端无法被摊薄等问题。

**本文新增什么**：

1. **前端 FTU 融合**：尺度不变缩放 + 指数感知取模（用尾数模 + 2 的幂模表，避免物化 110-bit 整数）；行/列统计在 DMA 中顺带完成；base-13 limb 编码流水化。目标：FTU 吞吐 ≥ 阵列每周期操作数需求，不成为瓶颈。
2. **CRT epilogue 融合**：每个模数 GEMM 完成后立即做 mod pᵢ、加权乘加、128-bit 累加；全部模数完成后统一 mod P/反缩放/舍入；中间结果不落 HBM。
3. **双缓冲与重叠**：余数平面双缓冲；FTU(i+1) 与 GEMM(i) 重叠；CRT(t-1) 与 GEMM(t) 重叠；用 tile 级流水把后端藏到 GEMM 后面。
4. **自适应 N/算法/分块**：用精度合同（BOUNDED/FAST）减少小矩阵的 N；按 K/B/动态范围在 I 与 II 之间切换（默认 II，I 作小 K/低精度回退）；K-block 与 batch 让阵列保持高利用；对小矩阵做批处理/持久化 kernel，摊薄启动与填充。

**量化目标**：K=1024–4096 时非 GEMM 开销 <10%；有效吞吐相对 GPU 软件模拟 ≥2×；HBM 流量不随 N 线性增长；精度合同可验证。

**与 OzCore 的差异**：OzCore 已把前/后处理整数化并流水；本文的增量是 **指数感知取模/尺度不变缩放的 FTU 微架构 + 小矩阵的 N/算法/分块自适应 + 批处理/持久化 + CRT epilogue 双缓冲**。需要逐条对照 OzCore 的数据流，不能把“无 HBM”直接当作独有增量。

**验证**：周期级模拟器与 RTL 对比；K=1024–4096 的非 GEMM 分解；与 OzCore 报告值同口径对比；对抗输入下的守卫/回退开销。

### 3.4 创新点 I3：存储/数据流协同

**OzCore 已有什么**：tile 级 pre/post 流水；但未系统回答 N 个余数平面在片上/片外的放置、双缓冲深度、SRAM 带宽与小矩阵 tile 调度的关系。

**本文新增什么**：

- **余数/limb 平面片上双缓冲**：当前模数 GEMM 与下一模数 FTU 重叠；平面不落 HBM；
- **tile/K-block 协同**：按输出 tile（如 128×128）与 k-block（64–128）设计 SRAM 容量/带宽；小 K 时用 K-block 融合与输出驻留，避免反复搬入；
- **HBM 流量与 N 解耦**：只与 A/B/C、缩放/权重表、tile 数相关，不随 N 线性增长；
- **批处理/流式**：小矩阵 batch 化、持久化 kernel，摊薄启动/填充；对延迟敏感场景评估子阵列并行。

**与 OzCore 的差异**：从“前/后处理流水”推进到“余数平面 + tile/K-block + 批量”的数据流协同，重点服务小矩阵的低算术强度。**验证**：HBM 流量、SRAM 带宽、阵列利用率、非 GEMM 开销随 K 的变化。

### 3.5 创新点 I4：同面积评估 + FPGA/FireSim 系统验证

**OzCore 已有什么**：相对融合多格式基线的等精度比较；没有相对同面积原生 FP64/FP32 的对照，也没有 CPU+加速器的可运行系统。

**本文新增什么**：

- 在目标工艺上综合 INT8/FP32/FP64 MAC 与阵列，标定 a₆₄、a₃₂、e₆₄、e₃₂；
- 建立同面积/同功耗/同带宽/同精度保证的归一化框架：把原生阵列缩放到与 OGE 相同面积，再比较有效吞吐、能效与精度；
- 给出“工艺比例 × 矩阵形状 × 精度目标”的可行性包络与 Go/No-Go 判据；
- **Chipyard + FireSim/Alveo U250**：构建 Rocket/BOOM CPU + OGE 的 SoC，运行 BLAS 风格库与 1–2 个应用；U250 用 32×32 或 16×16 缩比阵列（完整 128×128 约 16K MAC，U250 资源放不下），全尺寸用 FireSim/ASIC 综合评估；
- 端到端验证：CPU 发起 `oge_gemm` → 驱动/队列 → OGE → 精度统计回读；与 MPFR/GPU 对比；测延迟、吞吐、非 GEMM 开销。

**与 OzCore 的差异**：补上“同面积原生 FP64/FP32”与“可运行 CPU+加速器系统”两维，把统一引擎的价值从 kernel 级推进到系统级。**验证**：a₆₄ 曲线、端到端应用、FPGA demo、精度合同回读。

### 3.6 新颖性主张（谨慎版）

1. **微架构**：提出可综合的 INT8-only 统一精度 Ozaki GEMM 架构，把指数感知 FTU、INT8 阵列、宽整数 CRT epilogue 与精度合同融合到单一片上数据通路；相对 OzCore 增加小矩阵数据流、合同/守卫与系统验证。
2. **精度作为一级设计变量**：把误差界与阵列规模、模数集、累加器宽度、片上存储、带宽联合优化，给出可证明误差界下的 Pareto 前沿与自动配置。
3. **小矩阵非 GEMM 开销**：给出以小矩阵困难区间为目标的 FTU/CRT/双缓冲/自适应 N 的 RTL 级证据，把非 GEMM 开销从 27–55% 压到 <10%。
4. **同面积 + 系统验证**：给出同面积/同功耗/同带宽/同精度保证的模拟 vs 原生 FP64/FP32 对比框架，并用 Chipyard/FireSim/U250 做 CPU+加速器的端到端验证。

本报告不使用“首个/首次”作为无条件表述；所有“首次”均限定在“据我们所知 + 可综合 RTL + 同面积/系统证据”的组合上，并在投稿前做 FTO 与相关工作核查。多基不作为核心新颖性主张。

## 第 4 章 研究内容与技术路线

### 4.1 OGE 总体架构

OGE 由五部分组成：

1. **前端 FTU**：行/列统计与缩放、指数感知取模、limb 编码、平面打包；
2. **INT8 主阵列**：128×128 的 INT8 阵列（主线）；FP8/FP4 作为 WP6 可选扩展，不作为主线；
3. **CRT/加权后端**：模归约、8×128 权值乘加、128-bit 累加、mod P、反缩放与舍入；
4. **精度合同与调度器**：合同解析、N/算法族/缩放/分块选择、守卫、统计；
5. **存储层次**：A/B tile 双缓冲、余数平面双缓冲、CRT 权重表、输出缓冲。

数据流：A/B tile → FTU 生成余数/limb 平面 → 阵列逐模数 GEMM → epilogue 立即 mod/加权/累加 → 全部模数完成后 mod P/反缩放/舍入 → 写回 C。中间平面不落 HBM。

### 4.2 前端 FTU

- **统计与缩放**：按行/列计算 max|x| 与 Σx²；缩放因子是 2 的幂，乘以它只是指数加减；Σx² 可在 DMA 搬运时顺带计算；
- **指数感知取模**：把 a=(−1)^s·M·2^{e−52} 缩放后写成 A′=M·2^{e−52+μ}；计算 A′ mod pᵢ 用 ((M mod pᵢ)·(2^{e−52+μ} mod pᵢ)) mod pᵢ，只需小乘法器与 2 的幂模表；
- **limb 编码**：base-13 的贪心分解（约 15 步）可做成迭代单元或查表流水线；
- **布局打包**：按 TN 布局写入片上 buffer，生成缩放/CRT 权重索引。

### 4.3 INT8 主阵列与可选多基扩展

- **INT8 主线**：1 GEMM/模数，INT32 累加；128×128 阵列，默认模数串行（单阵列复用）；
- **可选多基（WP6）**：FP8 每模数 3 次 FP8 GEMM（FP32 累加）；FP4 base-13 limb 约 4 GEMM/模数（FP32 累加）；仅在“平台峰值比不可设计”或“需要原生低精度模式”时启动；
- **调度**：模数顺序、双缓冲深度、tile 大小、子阵列并行由 DSE 决定；小矩阵优先保证阵列利用率与非 GEMM 重叠，而非峰值；
- **面积取舍**：多基会增加 MAC 面积（FP8/FP4 为 INT8 的 1.46–1.64×），因此默认不启用；若启用，需在同面积评估中计入。

### 4.4 CRT/加权后端

- 模归约：对每个模数结果做 mod pᵢ；
- 加权：C′ᵢ·(P/pᵢ)·yᵢ，用固定宽度整数乘加；
- 累加：128-bit 宽整数累加，避免中间溢出；
- 收尾：mod P、反缩放、正确舍入/截断；
- 可重构：按 s/N 配置 slot 分组，支持不同吞吐/面积权衡。

### 4.5 精度合同与运行时守卫

- **合同语义**：EXACT / BOUNDED(ε) / FAST；
- **选型**：根据目标格式、误差界、动态范围、矩阵形状，选择算法族（默认 II，I 作回退）/N/缩放/分块；物理基默认 INT8，多基仅在 WP6 启用；
- **守卫**：缩放上界 vs P/2；重构后范围检查；溢出/次正规/特殊值检测与回退；
- **统计**：ulp 分布、正确舍入比例、实际配置；应用可读；
- **回退**：守卫失败 → 增大 N 或切到安全路径（原生/更高精度模式）。

### 4.6 存储层次与分块

- tile 工作集：输出 128×128、k-block 64–128；
- 余数/limb 平面双缓冲：当前模数 GEMM 与下一模数 FTU 重叠；
- SRAM 容量与带宽按 tile 设计，不随问题规模增长；
- HBM 流量只与 A/B/C 及缩放/权重表相关，不随 N 线性增长；
- 对 1024–4096 的“困难区间”做专门的带宽/延迟 DSE。

### 4.7 模型、算法族规则与 DSE

- 代价模型：计算（GEMM 次数 × 阵列吞吐）、变换（FTU 吞吐）、重构（宽整数）、存储（SRAM/HBM 带宽）、面积/能耗；
- 输入：a₆₄/a₃₂、CRT 面积/GEMM 面积、SRAM 密度、矩阵形状 K、目标精度 B、动态范围；
- 算法族：默认 Ozaki II；用交叉点模型判断何时切到 Ozaki I（小 K、低 B、CRT 后端占比高时 I 可能更优）；该规则是 WP1 的一条启发式，不单独作为创新点；
- 物理基：默认 INT8；FP8/FP4 仅在 WP6 的可选场景评估；
- 输出：N/算法族/缩放/分块的最优组合、K/B/动态范围相图、选型规则；
- 用 Python 实现 `oge_model.py`，与文献数字对齐（误差 ≤20%），并用 RTL 综合数据修正。

### 4.8 软件与编程模型

- BLAS 风格 `oge_gemm(A,B,C,precision,accuracy)`；
- 精度合同 API；返回实际 N/基/缩放与精度统计；
- 与 PyTorch/NumPy 的桥接；与 GEMMul8/ozIMMU/cuBLAS 的对比脚本；
- 驱动/寄存器接口；精度统计导出。

## 第 5 章 实验方案与评估方法

### 5.1 指标

- **有效吞吐**：目标精度下的 GEMM 吞吐（TFLOPS/TOPS），按 Q_eff 折算；
- **面积效率**：TOPS/mm²；**能效**：TOPS/W；
- **AEE**：T_eff/(A×P)，按目标精度归一化；
- **非 GEMM 开销**：变换/重构/模归约时间占比；
- **存储**：HBM 流量、片上 SRAM 容量/带宽、中间平面是否落 HBM；
- **精度**：相对误差、ulp 分布、正确舍入比例、最坏情况界；
- **同面积**：a₆₄/a₃₂ 标定；原生阵列缩放到同面积后的加速比/能效比。

### 5.2 基线

- 原生 FP64/FP32/FP16/BF16 GEMM（同工艺、同面积/同功耗缩放）；
- 融合多格式阵列（OzCore 的基线口径）；
- OzCore（INT8-only，s∈{2,3,4,6,12}）；
- GPU 软件模拟（cuBLAS ADP、GEMMul8、ozIMMU，若 GPU 可用）；
- CPU AMX/SVE2（可选）。

### 5.3 工作负载

- GEMM 形状：1024–16384，覆盖“困难区间”与大规模；
- 精度目标：FP64/FP32/FP16/BF16；
- 动态范围：窄/宽/极端（含对抗输入）；
- 应用：LLaMA-3.1 PPL、HPL trailing update、量子化学 DGEMM、张量网络收缩；
- 合成 trace：按层/算子的精度需求混合，评估统一阵列的利用率。

### 5.4 工具链

- Python 模型（`oge_model.py`）；周期级模拟器（Python/C++）；
- RTL：SystemVerilog/Chisel；Verilator 功能验证；
- 综合：TSMC 28 nm HPC+ / ASAP7 / OpenROAD；DC/PrimeTime；
- FPGA：Chipyard + FireSim/Alveo U250（CPU+OGE 系统验证；U250 用 32×32/16×16 缩比阵列，全尺寸用 FireSim/ASIC 综合）；
- 黄金模型：MPFR；差分测试/形式化守卫。

### 5.5 同面积评估流程

1. 综合 INT8/FP32/FP64 MAC 与阵列，得到 A、P、频率（FP8/FP4 仅 WP6 可选）；
2. 计算 a₆₄=A_FP64/A_INT8、a₃₂=A_FP32/A_INT8、e₆₄/e₃₂；
3. 把原生 FP64/FP32 阵列缩放到与 OGE 同面积（或同功耗），得到原生有效吞吐；
4. 对每个目标精度/矩阵形状，计算 OGE 的 Q_eff、T_eff、AEE；
5. 画可行性包络：x 轴 a₆₄（或 a₃₂），y 轴加速比/能效比；标出盈亏平衡与 Go/No-Go 区间；
6. 报告“纯计算面积”与“系统级利用率”两个口径，避免混淆；
7. **FPGA/FireSim 系统验证**：Chipyard 生成 Rocket/BOOM + OGE 的 SoC；U250 上 FireSim 跑 CPU+加速器；执行 `oge_gemm` 与 1–2 个应用，测端到端延迟/吞吐/非 GEMM 开销，并回读精度统计。

### 5.6 前期结果（支撑开题）

- **P0（SMIC 28 nm）**：INT8 MAC 1281.67 µm²/767 cells/0.585 mW；4-lane 阵列 4847.14 µm²；128×128 外推 19.85 mm²、8.74 W、9.83 TOPS → 1.13 TOPS/W；相对 OzCore 面积 4.6×、默认功耗 18.6×。
- **P0b（TSMC 28 nm HPC+ FF，同 RTL）**：INT8 MAC 378.13 µm²/365 cells/0.366 pJ；关键路径 1.13 ns；与 OzCore 的 265.4 µm²/MAC 差 1.42×。说明 P0 的 4.6× 主要来自库密度，后续统一用 TSMC 28 nm。
- **Ozaki-II 三基 pass 数**：BF16/FP16/FP32/FP64 下，INT8 4/4/8/15 次；FP8 9/12/18/39；FP4 有效 9.9/11.9/19.8/37.5。等精度成本 INT8 最优；FP4 为 1.96–2.36×，FP8 为 3.17–4.23×（单 lane），阵列级 FP4 2.20–2.64×、FP8 3.53–4.71×。
- **MAC/阵列实测**：FP8 MAC 619.42 µm²/0.315 pJ；FP4 551.25 µm²/0.200 pJ；128×128 阵列（8×8 tile 实测 + 256 tile 组合）INT8 5.903 mm²/1.800 W、FP8 10.765/1.549、FP4 9.633/0.982；INT8 面积最小。其中功耗为单 lane 实测默认活动率能量 × 16384 的模型值（tile DC 功耗不随 lane 线性缩放）。
- **结论**：在 28 nm、自研 ASIC 的设定下，INT8 基是等精度面积—能耗最优；因此主线收敛为 **INT8-only**，FP8/FP4 仅作为 WP6 可选扩展（平台峰值比不可设计或原生低精度模式时启用），不作为核心创新。
- **待补**：FP32/FP64 原生 MAC 的 a₃₂/a₆₄ 综合（M1 首要任务）；当前只有 OzCore 文献值与我们的 INT8 实测，不能替代目标工艺标定。

**Go/No-Go 判据**：

- M1：若目标工艺 a₆₄ < 17–25（或 a₃₂ < 8–11），则 FP64 纯计算优势不成立；转向 FP32-first、能效/灵活性主张，或 MVP-1 测量论文。
- M2：若模拟器显示小/中矩阵非 GEMM 开销无法压到 <15%，则调整融合方案或把主战场移到大规模 GEMM。
- M3：若 FTU/CRT 综合面积超过预算 25%，则改用分时复用/两级 CRT，或缩小 N_max。
- M4：若 RTL 无法在目标频率收敛，则降低频率/提高流水级数，保功能与面积结论。

## 第 8 章 风险与应对

| 风险 | 触发 | 应对 |
|---|---|---|
| a₆₄/a₃₂ 不足 | M1 综合低于阈值 | 转 FP32-first；强调能效/灵活性/系统利用率；MVP-1 负结果论文 |
| RTL 工期超支 | M3 模块未收敛 | 关键模块优先（FTU/CRT），系统集成后置；用 Gemmini/Chipyard 复用 |
| 精度证明困难 | 守卫/最坏情况无法覆盖 | 限定有限非特殊值；特殊值回退；与数值分析合作；差分/形式化测试 |
| 非 GEMM 开销压不下 | 模拟器显示 >15% | 调整 tile/双缓冲/子阵列；把主战场移到大规模；诚实报告 |
| EDA 资源不足 | 28 nm/ASAP7 不可得 | 用 ASAP7/OpenROAD；面积结论标注工艺；与 OzCore 同工艺对比 |
| FPGA 资源/时序不足 | U250 放不下 128×128 或 FireSim 编译超时 | 用 32×32/16×16 缩比阵列验证系统；全尺寸用 FireSim/ASIC 综合；提前做资源估算 |
| 竞争/专利 | 投稿前 FTO | 逐条差异化；避免“首次”过度表述；做 FTO 分析 |
| 范围蔓延 | WP6 多基/多字/复矩阵 | WP6 增量，主线先 INT8 + 合同 + 小矩阵融合；多基仅 WP6，不占核心 |
